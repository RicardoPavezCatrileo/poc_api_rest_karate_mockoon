01 · El concepto

¿Qué es este POC?

Es una prueba de concepto de automatización backend: una API REST de usuarios (con autenticación) y un servicio SOAP, simulados con Mockoon en localhost:3001 y probados con Karate. Es la contraparte de la POC de Playwright con Pytest: las dos prueban el mismo mock y se comparan caso por caso.

🥋

Karate DSL

La solicitud y la validación se escriben en el mismo .feature, sin clases de prueba. match compara estructuras completas con marcadores (#string, #regex) y XPath para XML. Java 21 y un único runner de JUnit 5.

🎭

Mock en vez de backend

Mockoon simula CRUD, login, Bearer y API Key, 12 errores HTTP, una ruta que tarda 15 s y SOAP con WSDL. Los casos difíciles (errores, lentitud) se prueban sin depender de otro equipo.

🎯

Pensado para un cargo

Cubre lo que pide una oferta de QA Automation backend: REST y SOAP, OpenAPI, SQL, Gatling, monitoreo, Postman, curl, Git y Azure DevOps. La tabla de cobertura lo detalla requisito por requisito.

02 · El valor

¿Qué problema resuelve?

Muestra cómo probar un backend más allá del código de estado: contrato, datos, seguridad y rendimiento, con casos independientes que corren igual en local y en CI.

🧼

Cada escenario parte limpio

Los features que modifican datos llaman a common/reset.feature al inicio del Background (POST /api/test/reset). Cada escenario se puede ejecutar solo y en cualquier orden.

📜

Contratos, no solo respuestas

Cada respuesta REST se valida contra openapi.yaml y cada respuesta SOAP contra el XSD del WSDL. Un campo de más o un status no documentado falla, aunque el caso no lo revise.

🗂️

Datos fuera del código

Usuarios, credenciales, emails inválidos (CSV), payloads malformados y mensajes SOAP viven en src/test/resources/data. Un caso negativo nuevo es una fila más.

🔐

Seguridad explícita

401 frente a 403, WWW-Authenticate, API Key, y ningún campo sensible (password, token, hash…) en ninguna respuesta, en cualquier nivel del JSON.

🗄️

SQL para preparar y verificar

Una base H2 en memoria con usuarios, cuentas y movimientos: JOIN, LEFT JOIN, GROUP BY, HAVING y conciliación de saldos, siempre con consultas parametrizadas.

📈

Rendimiento con criterio

Los mismos features corren como carga en Gatling, con un SLA que falla el build (p95, p99, errores y TPS) y un monitor de CPU y memoria para ubicar el cuello de botella.

03 · Las piezas

¿De qué está hecho?

Seis capas. El QA trabaja arriba (features y datos); el resto se comparte entre todos los casos.

Todas las solicitudes HTTP de las pruebas las hace Karate. Las clases Java validan o preparan datos; no llaman a la API.

📌 La regla de oro: un caso negativo valida el código, el Content-Type y el cuerpo de error completo. Un 422 con el mensaje equivocado es un defecto, aunque el status sea el correcto.

🟢 Camino crítico

Listar, obtener, crear, login con token, SOAP y la consistencia API–base. Es lo primero que se corre tras un cambio.

.\mvnw.cmd test "-Dkarate.options=--tags @smoke"

@contract

📜 Contratos

OpenAPI para REST, XSD para SOAP y esquemas de Karate. Detecta cambios de la API que ningún caso revisa.

Validadores en soporte/; esperan == [].

@sql

🗄️ Datos

Preparar el dato con una consulta, consultarlo en la API y conciliar saldos de cuentas y movimientos.

H2 en memoria, modo PostgreSQL, recreada en cada escenario.

@security

🔐 Seguridad

401 frente a 403, tokens con formato inválido, API Key rechazada y ningún campo sensible en las respuestas.

Tokens fijos de laboratorio (no JWT).

@negative

🚫 Negativos

Datos inválidos desde JSON y CSV, payloads malformados enviados tal cual, recursos inexistentes y errores HTTP.

Cada negativo compara el cuerpo de error completo.

performance/

📈 Carga y estrés

Consultas, login y SOAP como usuarios virtuales en Gatling, con SLA, TPS mínimo y monitoreo de recursos.

No los ejecuta ApiTestRunner: van con gatling:test.

05 · De punta a punta

Qué pasa cuando se ejecuta un caso

Dos casos reales, de menos a más: primero un GET con esquema; después un escenario de SQL que prepara el dato en la base y lo verifica en la API.

1 · El caso más simple: listar los usuarios

# src/test/java/usuarios/get-usuarios.feature
@regression
Feature: GET /api/usuarios

  Background:
    * call read('classpath:common/reset.feature')
    * url baseUrl
    * def datos = read('classpath:data/usuarios.json')
    * def esquemaUsuario = read('classpath:common/schemas/usuario.json')

  @smoke
  Scenario: Listar los usuarios iniciales
    Given path 'api', 'usuarios'
    When method get
    Then status 200
    And match header Content-Type contains 'application/json'
    And match each response == esquemaUsuario
    And match response[*].id == datos.existentes

Maven ejecuta el runner

Surefire solo incluye ApiTestRunner; -Dkarate.options reemplaza sus rutas por este feature. karate-config.js entrega baseUrl y los timeouts.

.\mvnw.cmd test "-Dkarate.options=classpath:usuarios/get-usuarios.feature"

Background: datos limpios

reset.feature envía POST /api/test/reset y valida { status: 'restablecido' }: el mock vuelve a los 3 usuarios iniciales. Después se leen los datos y el esquema.

La solicitud

path y method get arman GET http://localhost:3001/api/usuarios. Karate guarda response, responseStatus, las cabeceras y responseTime.

Las validaciones

match each aplica el esquema a cada usuario; un campo de más o de otro tipo falla. Luego compara la lista de ids con la esperada.

// common/schemas/usuario.json
{ "id": "#number", "nombre": "#string",
  "email": "#regex [^@\\s]+@[^@\\s]+\\.[^@\\s]+",
  "rol": "#regex (admin|supervisor|usuario)", "activo": "#boolean" }

Resultado

El paso queda en verde en target/karate-reports/karate-summary.html, y la solicitud y la respuesta completas en target/karate.log.

2 · El siguiente nivel: preparar el dato con SQL y verificarlo en la API

# src/test/java/sql/datos-sql.feature
  Background:
    * call read('classpath:common/reset.feature')
    * url baseUrl
    * def db = Java.type('soporte.BaseDeDatos')
    * db.inicializar()

  Scenario: Preparar datos con SQL: el usuario activo con mayor saldo total se consulta en la API
    * text consulta =
      """
      SELECT u.id, u.nombre, SUM(c.saldo) AS saldo_total
      FROM usuarios u
      JOIN cuentas c ON c.usuario_id = u.id
      WHERE u.activo = TRUE AND c.estado = 'activa'
      GROUP BY u.id, u.nombre
      ORDER BY saldo_total DESC
      LIMIT 1
      """
    * def elegido = db.consultar(consulta)[0]
    * match elegido.saldo_total == 4700.50

    Given path 'api', 'usuarios', elegido.id
    When method get
    Then status 200
    And match response.nombre == elegido.nombre

La base se recrea

db.inicializar() ejecuta sql/schema.sql y sql/datos.sql en una H2 en memoria: tablas usuarios, cuentas y movimientos, con los mismos usuarios que el mock.

La consulta elige el dato

JOIN entre usuarios y cuentas, filtro de activos, SUM por usuario, orden descendente y el primero. BaseDeDatos.consultar devuelve filas como mapas, que Karate compara con match.

La API confirma

Con el id elegido se consulta GET /api/usuarios/{id} y el nombre debe coincidir con el de la base. Así se prueba que la API y los datos cuentan la misma historia.

06 · El flujo

Cómo se agrega un caso de prueba

Un caso solo está terminado cuando corrió contra el mock, se vio en el log lo que se envió de verdad y, si cambió la API, se actualizaron los contratos.

El mock, los contratos y los datos se cambian juntos: si uno queda desfasado, los escenarios de contrato lo detectan.

07 · Cuando algo falla

¿Falló la API, la prueba o el entorno?

Antes de tocar el código, la evidencia (reporte, karate.log y log del mock) dice cuál de las tres causas es.

🔧

Fallo técnico → se corrige la prueba

Un dato desactualizado, un esquema que no se ajustó o un escenario que olvidó el reset. La API está bien; la prueba quedó desactualizada.

🐞

Fallo funcional → defecto de la API

Un status distinto, un mensaje de error equivocado, un campo de más o una respuesta fuera del contrato. La prueba está bien; el servicio no. Se reporta el defecto.

🔌

Fallo de entorno → se revisa el mock

Mockoon detenido, Desktop y CLI peleando el puerto 3001, o un archivo de mock editado sin recargar. Se arregla el entorno y se repite.

⚖️ La regla que no se negocia: el caso es el criterio de verdad. Si la API no cumple el contrato o el mensaje esperado, el caso debe fallar. No se relaja un match para dejar en verde algo que el servicio no cumple.

Cómo revisar una falla

Leer el reporte

target/karate-reports/karate-summary.html marca el paso en rojo. El mensaje de match indica la ruta del JSON (o el XPath) y el valor esperado frente al recibido.

Ver lo que se envió de verdad

target/karate.log tiene la solicitud y la respuesta completas. Así se descubrió que header X = null envía el texto null y que un cuerpo vacío sale con Content-Length: 0.

Mirar el mock

En Mockoon Desktop, la pestaña Logs del entorno; con la CLI, --log-transaction. Si el mock no responde, el escenario falla en el primer paso (normalmente el reset).

Reproducir aislado

Un solo feature con -Dkarate.options=classpath:…, o la solicitud a mano con curl.exe. Si pasa sola y falla en la suite, el problema son los datos compartidos.

09 · El primer paso

El primer ciclo en 4 pasos

El camino mínimo para clonar el proyecto y ver la suite pasar.

Requisitos

JDK 21 y Node.js. Maven no hace falta: el wrapper descarga Maven 3.9.9 la primera vez.

java -version
node -v
.\mvnw.cmd -v

Levantar el mock

Con Mockoon Desktop (abrir mocks/usuarios-api.json y Start) o con la CLI en otra terminal. Nunca los dos en el mismo puerto.

npx.cmd @mockoon/cli@9.10.0 start --data .\mocks\usuarios-api.json --disable-log-to-file --log-transaction

Comprobar que responde

curl.exe http://localhost:3001/api/health

Ejecutar y abrir el reporte

.\mvnw.cmd test "-Dkarate.options=--tags @smoke"
Start-Process .\target\karate-reports\karate-summary.html
💡 Tip: para entender un caso, ejecútalo solo y abre target/karate.log al lado del .feature: cada paso method corresponde a una solicitud y una respuesta en el log.
